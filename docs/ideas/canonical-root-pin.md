# Canonical-root pin: the hub proves which store it is serving — or says it can't

**Status:** Idea — not committed. Added by `/replenish` (Harden lane) on 2026-08-12.
**Note:** Convergence: two blind lenses (Source-of-Truth-Drift · Silent-Wrongness's store self-identity, folded in).

_A machine-level pin naming the one checkout that counts, a `/api/health` readout that reports the paths the server actually resolved and whether they match it (true / false / unknown — never a guess), a non-dismissible "scratch copy — nothing here counts" banner in the app shell when they don't, and one preventative refusal so a non-canonical checkout can't take the phone-reachable port._

## Premise

Assumption #3 says one Mac is the single source of truth — but nothing in the code asserts *which* copy of the repo that is. Every root in `backend/app/config.py` derives from `Path(__file__).resolve()`, and no script anywhere sets `LEARNING_HUB_DATA` or `SWEEPS_DIR`, so the identity of the store is decided silently by which checkout the process was started from. This repo currently holds five live worktrees under `.claude/worktrees/`, and `backend/data/` is gitignored, so each one owns a private, empty store. The mechanism is not hypothetical: `.claude/worktrees/learning-paths/backend/data/learning-hub.sqlite` is a real 139KB store with the full schema and two `.bak-20260722T…` pre-migration siblings — a backend process genuinely booted against a worktree on 2026-07-22 and migrated a shadow database. What saved it was luck about *who* was talking to it, not any guard. This idea makes the server state the paths it resolved, compare them against a pin that lives outside every checkout, and say so loudly on the phone when they disagree.

**Why now:** The extended v1 verdict lands ~2026-08-19 and certifies on `mornings_phone` ≥5 + ≥3 notes/week — a metric read entirely out of one SQLite file whose identity nothing asserts. There are ~5 remaining phone-mornings of runway and five live worktrees on disk right now, one of them already holding a migrated shadow store. Certification is also the period with the most deploy churn (`git ff main` + `npm run build` + `launchctl kickstart`), i.e. the most windows where :8000 is momentarily unowned. After 08-19 this is ordinary hygiene; before it, it is the difference between a verdict on real data and a verdict on quietly thinned data — and the thinning is unrecoverable after the fact, because a missing morning and a morning that never happened look identical.

## The bet

The bet: that a wrong-store server is a live exposure during the certification window — that the deploy routine (`launchctl kickstart` after a build), an `install-server.sh` run from a worktree (which bakes `$WRAPPER` = that worktree's `serve/run-server.sh` into `~/Library/LaunchAgents/com.homebase.server.plist` permanently), or a `./dev.sh` in any window where the prod agent is down, leaves a gap where the tailnet URL serves a store the D12 tally never reads. The cost of losing that bet is asymmetric and time-boxed: a phone-morning and a note that land in a shadow store are invisible to the habit strip, while the D12 supply check reads *sweep files* and would still call the day readable — so the week burns a certification slot instead of extending, and the ~08-19 verdict is decided on thinned data nobody can see is thinned. What makes a veteran of this project react is the forensic detail, honestly stated in both directions: the worktree store has the full schema and two migration backups, so a backend really did run there — but `brief_visits` and `brief_notes` in it are both **0**, so no drift row has actually landed yet. The mechanism is proven; only the exposure is untested. A veteran will also notice the mirror: bug #5 already installed a guard so dev traffic can't reach prod data (`dev.sh`'s `BACKEND_PORT` check, `backend/tests/test_dev_port_guard.py`) — and nothing at all stops real traffic reaching non-prod data. The second thing a veteran will catch is the honesty trap this idea has to dodge: on a fresh clone, in CI, or on any machine with no pin, a boolean `canonical: false` would itself be a surface stating something the code doesn't know — violating assumption #5 exactly as loudly as the bug it guards. That is why the readout is tri-state, and why "says it can't" is in the title rather than an afterthought.

## Decisions / open questions

- Where the pin lives. Recommended: a one-line `~/.homebase/canonical-root` written by `serve/install-server.sh`. The alternative — deriving it from the installed plist's `__WRAPPER__` path — adds no new state and is self-truing, but means parsing a plist and is macOS-only, which the Linux CI lane would have to special-case. Not `backend/data/` under any option: that is the self-certifying trap.
- Tri-state vs boolean on `canonical`. Recommended: `true | false | null`, with `null` = 'no pin on this machine' and no banner. A boolean would report `false` on every fresh clone, every CI run, and every collaborator's machine — a surface asserting drift it cannot know about, which is the exact class of dishonesty assumption #5 forbids.
- Does the banner block anything? Recommended: no. Non-dismissible warning, full app still functional. Blocking writes in a non-canonical checkout would break every legitimate dev and worktree flow, and the harm being guarded is silence, not the writes themselves.
- What `install-server.sh` does when a pin exists and points elsewhere. Recommended: re-pin, but print a loud before/after diff — a genuine repo move must still work unattended, and refusing would make relocating the project a puzzle. An `HOMEBASE_REPIN=1` gate is the stricter option if the accidental-worktree-install case feels more likely than the move case.
- Scope of the `dev.sh` refusal. Recommended: refuse only at the phone-reachable prod port (8000) from a non-canonical root, leaving every other port free — dev from a worktree must stay ordinary and easy, and 8000 is the only port `tailscale serve` fronts.
- Does the sweep lane need the same pin? Open. The worktrees have no `data/sweeps` at all, so a `sweep.sh` run from one would create a private brief tree the archive never sees — the same failure on the read side. Flagged rather than solved here; if it ships in this pass it stops being S-shaped.
- Whether the deploy routine should assert the pin. Cheap follow-on: one `curl -s 127.0.0.1:8000/api/health | jq -e '.canonical == true'` line in the runbook so the kickstart step fails loudly instead of serving quietly.

## Credible first step

Three files, in this order. (1) `backend/app/config.py` — add `self.canonical_root` (resolve `HOMEBASE_CANONICAL_ROOT`, else a one-line `~/.homebase/canonical-root`, else `None`) and `self.is_canonical` (`None` when unpinned, else `canonical_root == backend_dir.parent`). Note the correction to the original sketch: the pin must NOT live at `backend/data/.homebase-root` — `backend/data/` is per-checkout and gitignored, so every worktree would ship its own pin and self-certify; `~/.homebase/` already exists on this machine (the overnight verifier put files there) and the repo references it nowhere, so it is free machine-level ground. (2) `backend/app/models.py:319` `HealthResponse` + `backend/app/api/health.py` — add `db_path`, `sweeps_dir`, `canonical_root`, `canonical: bool | None`, all straight off `settings`; the endpoint already takes `settings=Depends(get_app_settings)`, so this is additive. (3) frontend — `frontend/src/api/types.ts:306` mirrors the new fields, and the shell in `frontend/src/App.tsx` (the `<div className="min-h-full">` above the sticky header, ~line 88) polls health once on mount and renders `<Banner tone="warning">` naming the resolved `db_path` when `canonical === false`. Second correction to the original sketch: there is **no existing health poll** to hang this on — `api.health` at `frontend/src/api/client.ts:175` is dead code, zero call sites in `frontend/src`, so the poll itself is part of the work. Then `serve/install-server.sh` writes the pin next to where it already writes the plist, and `dev.sh` gains the mirror of its own `BACKEND_PORT` guard.

## Dependencies

No blocking dependencies; nothing here touches an LLM lane, so the moonshot freeze (D7) does not apply. Two ordering facts: the pin does not exist until `serve/install-server.sh` is re-run once on this Mac, and until then health honestly reports `canonical: null` rather than pretending — so the live confirm below requires that reinstall. The frontend half depends on adding a health poll that does not exist today (`api.health` has zero call sites), and on the existing `frontend/src/components/Banner.tsx` `tone="warning"` variant, which is already there and already tested. The shell-guard half rides `backend/tests/test_dev_port_guard.py`'s established pattern for exercising `dev.sh` without touching the real :8000. Should land before the ~08-19 re-grade to be worth its own premise; it is still worth shipping after, at lower urgency. Worth a line in `docs/M6_PLAN.md`'s deploy runbook and the MASTER_PLAN changelog per the repo's upkeep rule.

## Explicitly out of scope (revisit later)

Blocking or read-only-ing writes in a non-canonical checkout. Any change to how `mornings_phone`, `brief_visits`, or the D12 supply check are computed — this idea makes the store identifiable, it does not touch the metric. Reconciling, merging, or importing rows from an already-split store (there are none: both counters in the worktree store are 0). Deleting or gitignoring the worktree stores. Pinning the sweep lane (`sweep.sh`, `sweeps/schedule/*`, `data/sweeps`) — named as an open question, not built here. Any multi-machine or multi-user notion of "canonical". Reworking the existing bug-#5 dev guard beyond adding the mirror case.

## Identity/positioning note

none — this hardens assumption #3 in place and adds no new surface class, no new data, and no new LLM or acting lane.

## What it changes

The store stops being anonymous. `/api/health` becomes the machine-checkable answer to "which Home Base is this?" — usable by a curl in the deploy routine, not just by eyes. On the phone, a wrong-store server stops looking exactly like the right one: the archive being empty and the habit strip being short become a banner instead of an inference. `serve/install-server.sh` gains a second output beyond the plist — the pin — so the machine records which checkout is prod in a place no checkout can overwrite by existing. And `dev.sh` picks up the missing half of bug #5's guard: it already refuses to start when the prod agent holds :8000; now it also refuses to *become* :8000 from a non-canonical root, so the one port `tailscale serve` fronts can only ever be served by the copy that counts. Nothing about the habit metric, the sweep lane, or any write path changes — this is detection plus one refusal, deliberately.
