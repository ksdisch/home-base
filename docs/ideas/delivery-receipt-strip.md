# Delivery receipt: prove the brief left the Mac

**Status:** Idea — not committed. Added by `/replenish` (QuickWin lane) on 2026-08-12.
**Note:** Convergence: THREE blind lenses (almost-done · free-lunch · cheap-delight) proposed this move independently.

_Fold the already-written `backend/data/brief-delivery.jsonl` into `GET /api/brief/runs/summary` and add one clause to the existing `SweepLedgerStrip` on Today — "Emailed + texted" on a good morning, amber "iMessage: unsent" on a bad one — so the repo's only outbound lane stops failing as an absence._

## Premise

`sweeps/deliver_brief.py` appends `{ts, date, channel, ok, detail}` on every send and every failure, and `grep` across the repo says exactly one thing reads that file back: the script's own idempotency check, `_delivered_channels`. No config entry, no endpoint, no model, no component, no test outside `test_deliver_brief.py`. This is the identical shape the sweep-ledger readout already fixed for `.runs.jsonl` — whose endpoint docstring literally says "nothing ever read it back" — so the reader, the response field, the strip, and the honesty conventions all get copied rather than invented. The failure it catches is lane-specific and real: iMessage goes out via `osascript` on the launchd sweep lane where the Messages TCC grant lives, and macOS silently no-ops sends it dislikes; email goes via SMTP with a Keychain app password that can be revoked. Both fail as silence, and silence at 6:05 AM is precisely what a person who hasn't picked up his phone yet cannot distinguish from a quiet morning. "Best-effort delivery never fails a sweep" quietly became "delivery never tells you."

**Why now:** The delivery lane is the repo's first outbound send and it is days old (PRs #181/#183, HEAD d447174) — and it is now the only best-effort path with no receipt anywhere: audio has the player, sweeps have this very strip, Overnight has its queue. The live ledger holds three rows from a single day, so the instrumentation lands while the lane is still young enough that the first real failure hasn't been silently absorbed yet. The harder timing reason: the extended v1 verdict lands ~2026-08-19 and certifies on `mornings_phone` ≥5. If iMessage's TCC grant lapses and sends start silently dropping, the phone-morning count falls for a *delivery* reason and gets scored as a habit failure — contaminating the one verdict the whole project is currently waiting on, with no artifact anywhere that could later distinguish the two.

## The bet

The bet is that the amber clause stays rare enough to be believed. An honesty signal that cries wolf is worse than no signal — it launders the silence it was built to break — so three things must hold at once, and each is a real design call, not a default: (1) **last-row-wins per `(date, channel)`**, because the live ledger right now has two `email` rows for 2026-08-12 (14:45:33 and 21:26:09) and the documented retry is "delete the row and kickstart", so an any-row-failed reader would show amber forever on a morning the retry already fixed; (2) **the expectation is gated on `brief.mp3` existing for the day**, because `deliver_brief.py` returns 0 and writes *no row* when there's no mp3, no channels enabled, or the sweep died before the post-step — so a row-dump readout renders nothing on exactly the worst morning; (3) **only channels actually seen in the window are ever called unsent**, which keeps the gitignored `sweeps/delivery.json` (Kyle's own email + phone) out of the API entirely. A veteran of this repo would open with "you're instrumenting a three-day-old lane that has never failed, and your readout's own failure mode is the same silence" — and the answer is that the mp3-gated expectation is the whole difference between a receipt and a row dump. The same veteran would then nod at where the doctrine came from: `runs_summary()`'s docstring already argues that "a day missing from the ledger entirely is the loudest signal it carries and the easiest one to lose by iterating only over the dates that exist." This applies that settled rule one axis over — iterate the channels you expected, not the rows you found.

## Decisions / open questions

- Expectation oracle: mp3-exists + channel-seen-in-window (recommended) vs. reading `sweeps/delivery.json` for the enabled-channel list. The former keeps PII out of the API and adds no config path; the latter is more precise but imports Kyle's email and phone into a response model.
- A channel that has NEVER appeared in the ledger — report it as unconfigured, or stay silent? Recommend silent: it matches every other strip's honest-degrade contract (render nothing rather than guess), and a never-seen channel is indistinguishable from a deliberately disabled one without reading delivery.json.
- Placement: append to the existing `sweep-ledger-line` (one dense morning line) vs. its own clause in the rollup `<p>` with its own `data-testid`. Recommend the rollup clause, so the morning line stays the sweep's and the delivery signal sits beside the other absence signals (`no sweep:`, `thin:`).
- Window: report only `latest.date`, or the full 7-day rollup window? Recommend the mirror of the existing shape — positive receipt for the latest day, absences accumulated across the window.
- Show a send time at all? The ledger `ts` is UTC (`2026-08-12T21:26:09Z`) while every day in the strip is parsed local, so "6:07a" needs a deliberate conversion. Decide between "Emailed + texted 6:07a" and the conversion-free "Emailed + texted".
- Does an ok:true row whose `ts` predates the current mp3's mtime count as delivered? `_delivered_channels` says no (a regenerated brief re-sends once). The readout should probably inherit that rule rather than invent a second definition of "delivered".

## Credible first step

All five integration points verified present. (1) `backend/app/config.py` — add `self.brief_delivery_ledger = self.data_dir / "brief-delivery.jsonl"` into the ledger block at lines 87–117, beside `brief_chat_ledger` / `brief_calibration_ledger` / `brief_overnight_ledger`; it is the only ledger in the repo missing from config. (2) `backend/app/sweeps.py` — a `delivery_summary()` next to `runs_summary()` (line 786), reusing its tolerant line-skip pattern, collapsing to last-row-wins per `(date, channel)` and returning per-channel `{ok, detail, ts}` plus an `unsent` list. (3) `backend/app/api/brief.py` — extend the endpoint at line 557; the "was delivery expected?" oracle copies line 551's existing `(sweeps_dir / d / "brief.mp3").exists()`, and the reported day keys to the same `latest.date` the sweep line already names so the two clauses can never disagree about which morning they describe. (4) `backend/app/models.py` — add a `delivery` field to `BriefRunsSummaryResponse` (line 1057) and mirror it in `frontend/src/api/types.ts` (line 1056). (5) `frontend/src/components/SweepLedgerStrip.tsx` — one clause in the rollup `<p>`, in the same amber-span shape the `no sweep:` and `thin:` clauses already use, under the component's stated contract of rendering nothing while loading, on fetch error, or on an empty ledger. Tests extend `backend/tests/test_brief_runs.py` and `frontend/src/components/SweepLedgerStrip.test.tsx`, both of which exist.

## Dependencies

None blocking. `backend/data/brief-delivery.jsonl` is already written by the shipped `sweeps/deliver_brief.py` (PRs #181/#183) and exists live with 3 rows. The backend stays strictly read-only over it, consistent with why every other ledger lives under `backend/data/` rather than `data/sweeps/`. Zero LLM, zero network, no schema migration, no new table. The D7 moonshot-lane freeze does not apply (QuickWin lane), and nothing here touches the ~08-19 verdict's inputs.

## Explicitly out of scope (revisit later)

Re-sending or retrying from the UI — the documented retry stays Mac-side (remove the ledger row, kickstart the agent), and `--force` is explicitly not driven from a session. No notifications, alerts, or push on failure. No reading `sweeps/delivery.json` into the backend (PII). No change whatsoever to `deliver_brief.py`'s send behavior, ledger format, or exit codes. No multi-day delivery history page or per-channel drill-down. No email open/read receipts or any signal that requires the recipient side — this reports that the Mac sent, not that the phone received.

## Identity/positioning note

none — tethered. It reads one existing local file onto one existing strip: no new surface, no new route, no LLM lane, no write, no outbound call. It does not change what Home Base is; it extends an invariant Home Base already holds (assumption 5, honest trust readouts) to the one lane that shipped without it.

## What it changes

After this, no best-effort lane in Home Base can fail without leaving a receipt where Kyle already looks. The soul brief's assumption 5 — "trust readouts must be honest; no surface states a guarantee the code doesn't keep" — currently stops at the sweep; this extends it across the outbound boundary. Concretely, on a morning with no text, Kyle can tell from the strip whether the send failed, the sweep failed, or the MP3 never rendered — the difference between running the documented retry and shrugging — instead of SSHing to the Mac to grep a JSONL. And the documented retry itself becomes reasonable-about rather than blind: today you delete a ledger row you have never seen.
