# The Uncounted Morning — the habit metric counts POSTs that succeeded, not mornings that happened

**Status:** Idea — not committed. Added by `/replenish` (Harden lane) on 2026-08-12.
**Note:** Pairs with `listening-counts-as-a-morning` (QuickWin) — same certifying metric, different hole.

_Make the Today-page visit beacon survive an offline read: when the POST fails, queue that local day in localStorage and replay it on the next successful load as a server-classified, permanently-marked backfilled visit — and report on the habit strip how many of this week's phone mornings arrived by replay, so the certifying number can be read with them and without them._

## Premise

`sw.js` deliberately serves the last brief from `BRIEF_CACHE` when the network is gone, but line 84 (`if (event.request.method !== "GET") return;`) sends the visit POST straight to a network that isn't there, and `Brief.tsx:459` swallows the rejection with `api.logBriefVisit().catch(() => {})`. The morning that looks most like the habit — phone in hand, Tailscale flaky on cellular, cached brief rendering instantly — is exactly the morning that never reaches `brief_visits`. Nothing errors: `GET /brief/habit` returns a smaller `mornings_phone` and `HabitStrip.tsx:160` renders it as a fact. That number is what certifies v1 at the ~08-19 re-grade, and week 1 of the graded window already read 0 phone mornings against a ≥5 bar. The defect is not the missing row — it is that the strip reports a **lower bound as if it were a count**, so "didn't read" and "read offline" are indistinguishable, and D12's supply-vs-demand fork turns on telling them apart.

**Why now:** The extended v1 verdict lands ~2026-08-19, seven days out, and `mornings_phone` ≥5 is the certifying number (D12). Week 1 of the graded window (08-03→08-09) recorded 0 phone mornings and 1 note; instrumentation was checked healthy (98 lifetime visits, 2 phone visits on 08-11), which means the recorded low number is currently unfalsifiable — there is no way to tell a real habit gap from a beacon that died on cellular. PRs #181/#183 made this materially more likely, not less: the brief is now emailed and iMessaged with a tap-to-play tailnet link, so the intended read path is now "phone, off wifi, tap a link" — the exact network where the POST fails and the cached brief still renders. Landing the guard before the verdict is the only window in which it can inform the verdict at all.

## The bet

The one thing that must be true: at least some of Kyle's phone mornings are genuinely failing the `POST /brief/visit` while the cached brief renders — the hole is live, not theoretical. If every phone morning has working tailnet, this changes no number and the 0 is real. What would make a veteran of this project react: "you are changing the measuring instrument seven days before the verdict it decides." That reaction is correct and is the design constraint, not an objection to dodge — which is why the fix is built to be *subtractable*: every replayed row carries `replayed_at`, the strip shows the replayed count, and the verdict can be computed exactly as it would have been without the change. The second veteran reaction — "M6 says writes never queue" (`docs/M6_PLAN.md:64`, `sw.js:88`) — is answered by scope, not exception: a visit is an idempotent fact *about the client* ("this device, this local day"), not user content; notes and Ask still fail loud and never sync later.

## Decisions / open questions

- Does a replayed morning count toward the certifying `mornings_phone` ≥5, or only toward raw `mornings`? Recommend: it counts AND is separately reported, so Kyle rules either way at the ~08-19 verdict — the same both-numbers deferral #159 and D12 already chose rather than pre-deciding in code.
- Land it before or after the ~08-19 verdict? Landing mid-window changes the instrument during the measurement. Recommend land now and record the deploy date in the verdict entry: the alternative is certifying on an instrument that provably cannot distinguish didn't-read from read-offline, and the replay component makes the pre-fix number recoverable anyway.
- 7-day queue cap, or shorter? Recommend 7 — it matches the weekly bar, and anything longer lets a phone that was offline for two weeks re-seed an already-graded week after the verdict.
- Should the queue also fire when the POST succeeds but the brief was served from cache (`fromCache`)? Recommend no — that day already has a live row, and queueing on it would double-write.
- What time does `visited_at` carry on a replayed row — the claimed morning or the replay moment? Recommend a synthetic time on the claimed local day, with `replayed_at` holding the true arrival; only `day` feeds the metric, and conflating the two would make the ledger unreadable later.
- Should the graded window's already-lost mornings be reconstructible at all (e.g. from delivery-lane email/iMessage open signals)? Recommend NO — that is a back-classification guess, and #159 explicitly refused to back-fill unattributed rows for the same reason.

## Credible first step

One vertical slice, test-first, across verified files: (1) `frontend/src/pages/Brief.tsx:459` — replace `api.logBriefVisit().catch(() => {})` with a localStorage day-queue (`homebase.habit.visitQueue`, sibling of the existing `homebase.habit.morningsMilestone` in `HabitStrip.tsx:25`): on failure push today's local day; on every successful load, flush pending days through the widened endpoint. (2) `frontend/src/api/client.ts:207` — `logBriefVisit(occurredDay?: string)`. (3) `backend/app/api/brief.py:372` `log_brief_visit` — accept an optional claimed local day; treat it as untrusted client input exactly as `visit_source.py` treats `X-Forwarded-For`: reject future days, reject >7 days back, drop a day already present for that source; `source` stays server-classified from the live peer (a replay from the phone lands `phone`, from the Mac lands `mac-localhost` — no client-chosen bucket). (4) `backend/app/store/schema.py` — SCHEMA_VERSION 14→15, `MIGRATIONS[15] = ["ALTER TABLE brief_visits ADD COLUMN replayed_at TEXT"]` (additive/idempotent, matching the dict's stated contract) plus the same column on the `brief_visits` DDL at line 131; `record_brief_visit` (`db.py:223`) writes the claimed day into `day` and the true arrival into `replayed_at`. (5) **The count fix the candidate's `phone-offline` tag would have missed:** `brief_habit_weeks` (`db.py:283`) filters `r["source"] == PHONE` at line 335 — a new source string would land rows the certifying number silently ignores, i.e. the same bug in a new costume. Instead widen the query at `db.py:318` to `SELECT DISTINCT day, source, replayed_at` and add `mornings_phone_replayed` = phone days reached **only** by replay (no live phone row that day), so subtracting it reproduces the pre-fix number exactly. (6) `models.py:1099` `BriefHabitWeek` + `types.ts` + `HabitStrip.tsx:160` — render "(N on phone, M by replay)" beside the existing count, same both-numbers pattern #159/D12 already set. Tests: `backend/tests/test_brief_habit.py` (replay counted once, day cap, future-day reject, dedup, `mornings_phone_replayed` arithmetic), `backend/tests/test_visit_source.py` (claimed day never influences the bucket), `frontend/src/pages/Brief.test.tsx` (failed POST → remount lands exactly one backfilled day; a second remount lands none), `frontend/src/components/HabitStrip.test.tsx` (replay clause renders, absent when zero).

## Dependencies

Schema v15 migration must land in the same change as the write path (the `MIGRATIONS` dict is re-run on every `init_db`, so the ADD COLUMN must stay additive/idempotent per its own stated contract). Contract crosses `models.py` → `frontend/src/api/types.ts` → `HabitStrip.tsx`, so the `api-types-sync` / `contract-reviewer` pair applies. Requires a prod-hub deploy to affect real mornings (ff main + `npm run build` + `launchctl kickstart -k gui/$(id -u)/com.homebase.server`) — the prod server serves prebuilt `dist` with no auto-reload, so an unbuilt merge changes nothing on the phone. Consumer is the ~08-19 v1 re-grade (D12). Note the interaction with open bug #15 (no cross-process sweep guard) is nil; there is no overlap with the five open bugs.

## Explicitly out of scope (revisit later)

No offline queue for content writes — notes and Ask still fail loud, `sw.js` still bails on every non-GET, and the M6 rule is carved around, not amended. No back-classification of pre-v14 unattributed rows or pre-fix missing mornings; the 08-03→08-11 gap stays exactly as recorded. No user-agent sniffing and no desktop-over-tailnet vs phone split (still deliberately over-counting as `phone`, per `visit_source.py`). No background sync API, no service-worker involvement at all. No change to the v1 criteria themselves, the notes bar, or the supply-side readable-mornings check. No retry/reliability work on the sweep lane — that is a separate, larger finding.

## Identity/positioning note

none — fully tethered. It hardens an existing metric on an existing surface under assumption 5 (trust readouts must be honest); no new surface, no new LLM lane, no new acting capability, and the moonshot freeze is untouched.

## What it changes

`brief_visits` gains a nullable `replayed_at` (schema v15); `POST /brief/visit` gains an optional, server-validated claimed day; `BriefHabitWeek` gains `mornings_phone_replayed`; the habit strip gains one clause. Behaviorally: an offline phone morning stops vanishing, and the certifying number stops being a silent lower bound — it becomes a count plus an explicit, subtractable replay component. `app/mirror.py:96` (`list_brief_visit_day_sources`) inherits the replayed days as ordinary phone days, which is correct for the Mirror's sentence and needs no change. Nothing about content writes changes: notes and Ask still fail loud offline, and `sw.js` still refuses to queue anything — the replay lives in page code, not the service worker, so the M6 invariant is untouched at its enforcement point.
