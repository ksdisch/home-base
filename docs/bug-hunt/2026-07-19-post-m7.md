# Bug-hunt audit — Home Base (post-M7 surface)

**Date:** 2026-07-19
**Scope:** everything shipped since the 2026-06-26 hunt — the entire Home Base arc (sweeps pipeline + scheduler, news mode + For You, chat + course authoring lanes, SQLite store, frontend/PWA incl. sw.js v3, one-port serving/ops) plus the vendored contract surface.
**Method:** `bug-hunt` ultracode fan-out — 7 finder slices (subsystem × lens, incl. the vendored `contract-reviewer` agent) → adversarial verify → synthesize. 15 agents, ~1.05M tokens, ~27 min.
**Deliberate template deviation (stated per the skill):** verification was batched at ≤6 findings per verifier call (7 batch calls) instead of one verifier per finding, to stay inside this session's multi-lane agent ceiling. Each batch kept the template's contract verbatim — verifiers opened the real files, defaulted to refuted, ruled per-finding, and adjusted severities.
**Result:** 27 raw findings → **25 survived adversarial verification → 23 distinct after synthesis dedup** (0 critical · 5 medium · 18 low). The `contract-reviewer` slice's 2 drift claims were **both refuted** — the backend↔frontend contract surface is clean. Several findings were reproduced by execution; five severities were downgraded in verification, so the list is **calibrated-low, not inflated**.
**Status: triage-only.** Nothing here has been fixed — this session's mandate ends at the ranked list; fixes are follow-up sessions (offer: `systematic-debugging` per picked finding).

## Themes

- Documented contracts the code doesn't enforce — the single biggest root cause (9+ findings): 'never a 500' (OSError gaps in sweeps.py, compute_streaks), 'no tools/grounded' (chat/regen), 'rolls back byte-identical' (course writer), 'never mislabeled developing' (_norm_url), 'runs the missed job on wake … or off' (plist), 'no restart needed' (serving README vs startup-time mount), 'sweep picks it up tomorrow' (scout add), 'writes disabled offline' (delete button). The fix pattern is the same everywhere: make the promise structural or correct the promise.
- UTC-vs-local-day bucketing with a known in-repo precedent: brief_visits was deliberately fixed to local days with a docstring explaining the 7pm-CDT hazard, but the activity/streak table and the foryou persistence gate were left on UTC — one root cause, two confirmed findings, and a grep for date('now')/now_utc()[:10] would likely close it repo-wide in one pass.
- Newest-wins / all-or-nothing selection with no content validation: latest_sweep_date trusts the newest folder regardless of servability, and get_category_items discards all healthy feeds when one fails — both convert partial failure into total user-visible failure on trust-critical surfaces.
- Non-atomic and unserialized file writes to live-served paths: render_brief.py's topic JSON, courses/writer.py's manifest, and append_roster_topic's race — while audio_brief.py already demonstrates the correct tmp+os.replace pattern in-repo; adopt it uniformly and add one lock for the dual-writer roster.
- Test suites cover happy paths and total-failure but systematically miss partial-failure and boundary edges: empty-newest-dir with an older good day, one-of-four feeds down, exception between write and restore, delete-while-filtered, path change mid-load, day-boundary timestamps (all tests pin 12:00 UTC) — the verifiers repeatedly found the bug living exactly in the untested middle state.
- Shipped-feature pairs that were never integration-tested against each other: scout add vs sweep.sh's prompt requirement, the M6 KeepAlive server vs make dev on port 8000, and the installer's build-later hint vs the startup-time frontend mount — each is two individually-correct artifacts with a broken seam.

## Calibration

Every survivor carries a code-level trace to exact `file:line`; the verifiers reproduced the mechanically checkable ones by execution (e.g. the `_norm_url` query-string collision) and downgraded five inflated severities (two mediums → low among them). The one low-confidence item (#23, `claude -p` tool enforcement) is flagged as such because its exploitability rests on CLI defaults unprovable from this repo alone. The two findings cut in synthesis were cross-dimension duplicates (the empty-sweep-dir blanking was found independently by the sweeps and serving-ops finders and merged; likewise one UTC-day overlap). Zero unverified claims remain.

## Detailed findings

### 1. Empty or all-failed newest sweep dir blanks the entire brief while yesterday's complete brief sits one folder down (dedupe: sweeps + serving-ops)

**Severity:** medium · **confidence:** high · **location:** `backend/app/sweeps.py:62-67`

**Why it matters:** sweep.sh mkdir-p's the day folder minutes before the first topic lands, and latest_sweep_date has no content check, so every morning there is a window — exactly when the on-wake catch-up fires and Kyle opens his phone — where GET /api/brief says has_data=false ('no sweeps yet'), audio 404s, and chat is unusable. On a fully failed sweep day (only .raw.txt) the previous day's good brief is hidden all day. This lands squarely on the riskiest assumption: the brief looking broken at wake-up is how the habit dies.

**Suggested fix:** Make latest_sweep_date (or a wrapper shared by brief/audio/chat) skip date dirs containing no *.json/*.md, returning the newest day with renderable content; optionally expose the newer folder's in-progress/failed state explicitly.


### 2. Scout one-click add creates a roster topic with no sweep prompt — the topic never sweeps and every subsequent daily sweep exits 1

**Severity:** medium · **confidence:** high · **location:** `backend/app/news.py:83-107`

**Why it matters:** append_roster_topic writes only the topics.json entry; sweep.sh requires prompts/<slug>.md per topic and counts its absence as a failure, so the run ends rc=1 forever after. The shipped, advertised M7 feature ('tomorrow's 06:00 sweep picks it up') silently does nothing from the phone, and the daily failure is visible only in a log nobody reads.

**Suggested fix:** Have append_roster_topic also write sweeps/prompts/<slug>.md from a generic template parameterized by the term (matching the M0-tuned sourcing bar), or make sweep.sh fall back to a generic prompt instead of a permanent failure; at minimum surface the missing-prompt state in the add response.


### 3. One dead feed in a multi-feed category discards all successfully fetched feeds and freezes the category on an ever-staler cache

**Severity:** medium · **confidence:** high · **location:** `backend/app/news.py:183-191`

**Why it matters:** The try wraps the whole feed loop, so one flaky host (Uplifting has 4 independent small WordPress sites; Local has 2) throws away the feeds that succeeded and serves the expired cache as stale — and the category can never refresh while that single feed stays down, even though the others are healthy. Permanent staleness of a whole tab directly undercuts trust in the news mode.

**Suggested fix:** Catch NewsFeedError per feed and continue; serve/cache the merged result as fresh when at least one feed succeeded; only fall back to stale cache / 502 when every feed failed. Add a partial-failure test.


### 4. Learning-activity days are bucketed on the UTC calendar day — evening Chicago use files under tomorrow and breaks streaks

**Severity:** medium · **confidence:** high · **location:** `backend/app/store/db.py:80 (also :108, :356, :443, :510, :645, :756, :978, :1054; reader api/progress.py:64)`

**Why it matters:** Any activity after ~7 PM CT lands on tomorrow's UTC day, so consecutive local-day practice reads as a broken streak and an evening dashboard check can show current_streak=0 while it's still 'today' locally. The repo already diagnosed and fixed this exact bug for brief_visits (schema.py:117-120 spells out the 7pm-CDT hazard) — the activity table serving identical 'did I do it today' semantics was left on UTC.

**Suggested fix:** Write activity.day as the local day mirroring record_brief_visit: date('now','localtime') in the six raw-SQL writers, local-day derivation in record_attempt/record_flashcard_review, and datetime.now().astimezone().date() as 'today' in api/progress.py.


### 5. make dev silently runs against the KeepAlive prod server — both claim port 8000, dev writes mutate prod data

**Severity:** medium · **confidence:** medium · **location:** `dev.sh:64`

**Why it matters:** With com.homebase.server installed, the dev uvicorn dies at bind in a backgrounded subshell, Vite comes up anyway and transparently proxies /api to the prod agent: backend edits never take effect (no --reload process) and dev-frontend writes land in the prod SQLite/ledgers. Everything appears to work, which is the dangerous part — this is the same Mac the repo is actively developed on.

**Suggested fix:** Before launching uvicorn, detect the taken port (lsof -ti tcp:8000 or a health-check curl) and fail loudly naming com.homebase.server; or move dev backend + Vite proxy to a distinct port (8001) so dev and the agent never collide.


### 6. Read-time dedup URL identity strips the whole query string — different articles on query-keyed URLs falsely match, mislabeling fresh items 'developing' with a wrong first_seen

**Severity:** low · **confidence:** high · **location:** `backend/app/sweeps.py:152-158`

**Why it matters:** youtube.com/watch?v=AAA and ?v=ZZZ collide to 'youtube.com/watch' (reproduced by execution), violating the docstring's 'conservative … never mislabeled' invariant. Sports-topic sweeps plausibly cite query-keyed URLs across a week, and a false 'developing · first seen <date>' label on a fresh story is exactly the silent trust erosion the product can't afford.

**Suggested fix:** Keep the query string in the normalized identity (strip only fragment/trailing slash, or only known tracking params like utm_*/fbclid); add a regression test with two watch?v= URLs.


### 7. GET /api/brief can 500 on an unreadable sweep file — OSError missing from the read-path except clauses, breaking the never-500 contract

**Severity:** low · **confidence:** high · **location:** `backend/app/sweeps.py:253-262 (and _fallback_topic line 127)`

**Why it matters:** One bad permission or a mid-swap replacement takes down the whole Today page instead of degrading a single topic. Every other read in the module deliberately catches OSError; the two brief-serving reads — including the designated fallback path — are the exceptions, so this is drift against the module's own contract.

**Suggested fix:** Add OSError to the except tuple at line 257 and wrap _fallback_topic's md read in try/except OSError falling through to the 'no readable brief' dict.


### 8. Frontend mount decided once at startup, but installer/README promise 'make build' needs no restart — fresh installs serve API-only forever

**Severity:** low · **confidence:** high · **location:** `backend/app/main.py:74-76`

**Why it matters:** install-server.sh explicitly tolerates a missing dist and tells you to 'run make build', but the KeepAlive process registered no SPA catch-all at startup and never restarts — the phone 404s on / until a launchctl kickstart nobody mentions. Two shipped artifacts in the same feature contradict each other on the exact out-of-order path the installer's own warning anticipates.

**Suggested fix:** Register the catch-all unconditionally and check frontend_dist per request (serve index.html when present, 404 when not), making the README claim true; or amend the installer hint/README to include the kickstart command.


### 9. One malformed activity.day row permanently 500s GET /api/progress via compute_streaks

**Severity:** low · **confidence:** high · **location:** `backend/app/store/progress.py:32`

**Why it matters:** date.fromisoformat runs unguarded over every distinct activity.day, so a single bad row (reachable via the vendored learning-hub-db MCP write_query — the same outside-the-app surface behind the documented 2026-07-16 incident) takes down the whole progress dashboard despite the module's 'Never a 500' promise. The sibling brief_habit_weeks reader already skips malformed rows per-row with a test proving it.

**Suggested fix:** Parse defensively like brief_habit_weeks: wrap date.fromisoformat per row in try/except (TypeError, ValueError) and skip bad rows.


### 10. Subscription-lane env scrub drops only ANTHROPIC_API_KEY — ANTHROPIC_AUTH_TOKEN and Bedrock/Vertex switches can still silently flip billing to metered

**Severity:** low · **confidence:** high · **location:** `backend/app/chat.py:51-55 (also regen.py:86-90, sweeps/schedule/run-scheduled.sh:20)`

**Why it matters:** The documented guarantee ('a stray exported key can never silently flip a question onto metered API billing') is enforced for one variable out of the set the claude CLI actually reads. An exported ANTHROPIC_AUTH_TOKEN or CLAUDE_CODE_USE_BEDROCK/VERTEX from unrelated tooling meters every chat, regen, and sweep — the exact failure mode that motivated the scrub.

**Suggested fix:** Extend all three scrub sites to also drop ANTHROPIC_AUTH_TOKEN, CLAUDE_CODE_USE_BEDROCK, CLAUDE_CODE_USE_VERTEX (and ANTHROPIC_BASE_URL), and pin the full set in the scrub tests.


### 11. _strip_fence corrupts a regenerated lesson/exercise that legitimately starts and ends with distinct code blocks

**Severity:** low · **confidence:** high · **location:** `backend/app/courses/regen.py:204-210`

**Why it matters:** A correct unwrapped answer opening with starter code and closing with a solution block gets its outer fences stripped, leaving unbalanced markdown that passes validate_dir's non-empty-only check and is written with no rollback — a garbled lesson from a normal model output shape, no adversarial input needed. Markdown types have no downstream parse to catch it (JSON types would fail and roll back).

**Suggested fix:** Only strip when the fence is plausibly a wrapper (e.g. interior fence markers remain balanced after stripping); on ambiguity pass the text through unchanged. Add the false-positive test.


### 12. append_roster_topic read-modify-write race can silently lose a concurrent write to sweeps/topics.json

**Severity:** low · **confidence:** high · **location:** `backend/app/news.py:95-106`

**Why it matters:** Two Add taps (FastAPI runs these sync handlers on a threadpool, and the UI shows up to 3 Add cards) or a hand-edit saved mid-flight gets clobbered while both writers see 200 ok — silent data loss on a file the brief explicitly names as dual-writer. The shared fixed-name tmp file compounds it. The lost topic simply never appears at 06:00.

**Suggested fix:** Module-level threading.Lock around read→dupe-check→write→replace (sufficient single-process); use a unique tempfile for staging; optionally mtime-check before replace to narrow the hand-edit window.


### 13. Topic scout's '>=3 distinct days' persistence gate buckets by UTC day, not local day — an evening session spanning 7 PM CT counts as two days

**Severity:** low · **confidence:** high · **location:** `backend/app/foryou.py:270-274`

**Why it matters:** Same root cause as the streak bug: naive-UTC created_at truncated to a date with no conversion, so two sittings can satisfy a gate whose stated intent is 'a persistent interest, not one morning's rabbit hole', and the days_seen evidence on the suggestion card overstates persistence. schema.py documents this exact hazard for brief_visits; the fix wasn't applied here.

**Suggested fix:** Parse created_at, attach UTC when naive, convert to America/Chicago, then take .date() as the bucket — mirroring _decay's normalization.


### 14. Deleting the last note of the filtered topic strands the filter and shows a false 'No notes yet' empty state with no in-page recovery

**Severity:** low · **confidence:** high · **location:** `frontend/src/pages/Notes.tsx:34-84`

**Why it matters:** The stale topic filter hides all remaining notes behind a factually wrong 'No notes yet — add one from the Today brief' banner, and if only one topic remains the select unmounts so only a full reload recovers. Ordinary path for a notes page; data is intact, so cosmetic-but-confusing.

**Suggested fix:** Derive an effective filter: const effectiveTopic = topics.some(t => t.slug === topic) ? topic : 'all', used for both visible and the select value (or reset topic in remove() when deleting the filtered topic's last note).


### 15. Offline audio can be a different day's narration (or a broken player) presented as the cached brief's audio

**Severity:** low · **confidence:** high · **location:** `frontend/public/sw.js:76-86`

**Why it matters:** Brief JSON and audio age independently in BRIEF_CACHE with no date pairing — offline Saturday can play Tuesday's narration under Friday's brief, and on the iPhone (Range probes → 206 → never cached) the player renders then errors, defeating the 'no player, no 404 noise' guard. This is the stale-served-as-fresh failure the offline-honesty design exists to prevent, applied to audio.

**Suggested fix:** When fromCache, hide or honestly label the player; better, store the brief date alongside the cached audio and have the SW delete the audio entry when it caches a brief with a different date.


### 16. Per-note delete button stays enabled in offline (fromCache) mode, contradicting the offline banner

**Severity:** low · **confidence:** high · **location:** `frontend/src/pages/Brief.tsx:143-149`

**Why it matters:** The banner promises 'Notes and Ask are disabled until you're back online' and readOnly disables the two composers, but the ✕ delete escaped both the implementation and the dedicated offline test — tapping it fails with a generic 'Failed to fetch' that looks like an app bug. Writes never queue, so the hard invariant holds; this is a contract-consistency fix.

**Suggested fix:** disabled={readOnly} on the delete button with the same title treatment as the composers ('Offline — deletes need the hub').


### 17. Failed note delete renders under the 'Couldn't load notes' banner title

**Severity:** low · **confidence:** high · **location:** `frontend/src/pages/Notes.tsx:72-78`

**Why it matters:** Shared error state means a failed DELETE displays 'Failed to delete the note' under a hard-coded load-failure heading while the fully loaded list renders below — the heading misstates what failed and implies missing data.

**Suggested fix:** Neutral banner title ('Something went wrong') or a separate delete-error state with an accurate title.


### 18. Course write paths are not exception/crash-safe: an OSError mid-write skips rollback and can destroy course.json

**Severity:** low · **confidence:** high · **location:** `backend/app/courses/writer.py:52-63, 102-119`

**Why it matters:** The 'rolls back byte-identical' contract holds only when validate_dir returns ok:false normally; any raised exception (ENOSPC truncation, EACCES, validate_dir's own uncaught read_text, the second write in write_material) aborts before restore, and non-atomic write_text plus an in-memory-only backup means a crash can leave truncated JSON that list_courses silently skips — the course vanishes until hand-repair. Narrow trigger window, hence low.

**Suggested fix:** try/except around the write→validate sequence that restores snapshots before re-raising; write each file via tmp + os.replace; in write_material restore the material file if the manifest write raises.


### 19. On-wake catch-up does not cover a powered-off/rebooted Mac — a missed 06:00 fire is silently lost for the day, and the plist comment claims otherwise (dedupe: sweeps + serving-ops)

**Severity:** low · **confidence:** medium · **location:** `sweeps/schedule/com.homebase.sweep.plist.template:24-34`

**Why it matters:** launchd coalesces StartCalendarInterval fires missed during sleep only; with RunAtLoad=false, an overnight auto-update reboot or shutdown means no sweep all day, yesterday's brief served as latest, and nothing signals staleness — it looks like a quiet news day. The comment encodes the wrong mental model ('or off'), so this is shipped-behavior mismatch against M3's core hands-off promise, not a doc nit.

**Suggested fix:** Set RunAtLoad=true — already safe because SWEEP_SKIP_DONE makes an on-load fire a no-op on swept days — and fix the comment; optionally have GET /api/brief flag when the served date is older than today.


### 20. FlashcardReview load() has no cancellation — a stale deck's cards/queue can render under a newer ?path URL and grades corrupt the wrong deck's SM-2 state

**Severity:** low · **confidence:** medium · **location:** `frontend/src/pages/FlashcardReview.tsx:37-65`

**Why it matters:** The deck lives in a search param so React Router re-runs the effect without remounting; two racing loads let the last-resolved win regardless of currency, and grade() then POSTs the stale deck's index against the current path — server-side data corruption, not just cosmetics. Every sibling page uses the `let alive` pattern; this one missed it. Narrow trigger (back/forward between decks mid-load).

**Suggested fix:** Apply the house cancellation pattern: per-invocation token/alive flag, skip all setStates when a newer load has started.


### 21. Reorder failure revert restores a whole-course snapshot, clobbering concurrent lesson-completion toggles

**Severity:** low · **confidence:** medium · **location:** `frontend/src/pages/CourseDetail.tsx:147-168`

**Why it matters:** onToggle deliberately uses functional updates to compose concurrent toggles (per its own comment), but applyOrder's non-functional setCourse(prev) on the designed ok:false failure path rewinds a toggle whose POST already succeeded — UI and server disagree until reload. Requires a specific concurrency plus validation failure.

**Suggested fix:** Revert only what the reorder changed via a functional update that restores module order while preserving each lesson's current completed flag.


### 22. render_brief.py writes the live-served <topic>.json non-atomically

**Severity:** low · **confidence:** medium · **location:** `sweeps/render_brief.py:174-177`

**Why it matters:** write_text truncates then writes at the exact path the always-on server reads per request, so a reader in the window sees an 'unreadable <topic>.json' error card on the morning brief — transient but trust-damaging, and the .md fallback is written after the .json so it can also miss. audio_brief.py already uses tmp + os.replace for exactly this reason; the JSON writer predates it.

**Suggested fix:** Write both artifacts to .tmp and os.replace into place, .md first then .json, mirroring audio_brief.py's render().


### 23. Regen/chat lanes spawn claude -p with no tool restriction and inherited repo cwd — the 'no tools, grounded only in the item' contract is not structurally enforced

**Severity:** low · **confidence:** low · **location:** `backend/app/chat.py:108-129 (also regen.py:109-130)`

**Why it matters:** Nothing passed to the subprocess enforces the documented no-tools guarantee for permissionless read tools, and running from the repo root means the child loads this repo's CLAUDE.md/.claude settings into every chat/regen context. Code facts confirmed; concrete exploitability depends on headless -p's default permission behavior, which the repo can't prove — hence low confidence, hardening/contract-fidelity issue.

**Suggested fix:** Run the child with cwd set to an empty scratch dir (confines default reads, stops CLAUDE.md/settings pickup) and pass explicit tool denial (--disallowedTools or setting-sources isolation) in both chat.py and regen.py.
