Layer 4 is the harness: the code that got written most invisibly, and the part a skeptic loves to poke. The good news — every repo has the *same* shape, so you learn the plumbing once and navigate all six the same way.

## One model call

A run calls a small open model through **OpenRouter** (one API, many models: GLM, DeepSeek, Qwen, and tiny Qwen2.5 0.5–3B). Open the repo's `.env.example` and the model-call module and trace a single call: prompt in, model response out, parsed into the fields the oracle scores. That is the atom every experiment is built from; everything else is looping it and counting.

## The budget guard

Because these are paid API calls, every project runs under a **budget guard**: spend is tracked to the cent against a hard cap (typically under $5). If a run would exceed the cap, it stops. This is what makes "hobby scale" a *controlled* claim rather than a hope — `ghost-patch`, for instance, closed its whole chain for $1.42, tracked in a spend ledger you can open.

## The repo skeleton (learn it once)

Every repo navigates the same way. The standard parts:

- `README.md` — the claim, the headline, the honesty caveat.
- `DECISIONS.md` — the *why* log: every choice, tradeoff, and trigger you (or Claude Code, with your approval) made. If you read one file per repo, read this — it is where your defense lives.
- Milestone scripts (`m0`, `m1`, through `mN`, or stage runners) — one per experiment stage; `m0` is usually a gate or pilot run *before* paid data.
- A stats/verdict module — where Wilson (per arm) and Newcombe (per gap) are computed, and where a wrong-arm input exits `INVALID`.
- A committed `results/` directory — the recorded per-trial outputs, so the numbers are auditable, not retyped from notes.

## Worked example: where a number lives

Asked "where does `forge-gap`'s +32.5 pp come from?", the skeleton answers it: the arm counts live in `results/`, the Wilson/Newcombe math in the stats module, the *why-this-arm* in `DECISIONS.md` (D12), and the chart is drawn from already-measured numbers with no new model calls. Four files, the same four in every repo.

## ⚠️ Common mistakes

- **Diving into `mN.py` before `DECISIONS.md`.** The code says *what*; the decisions log says *why* — and "why" is what you get probed on.
- **Assuming the chart re-runs the models.** Charts are drawn from committed `results/`; the measurement already happened. Confusing the two invites a "did you re-run to get a nicer number?" hole.
- **Forgetting the budget guard exists.** "How do you keep it cheap?" has a concrete answer — a hard, tracked cap — not "I was careful."

## What to take away

1. One model call through OpenRouter, looped under a hard budget guard, is the whole engine mechanically.
2. Every repo has the same skeleton: README, `DECISIONS.md`, `m0` through `mN`, a stats module, committed `results/`.
3. `DECISIONS.md` is your single most valuable file; the reverse-learning protocol starts there.
